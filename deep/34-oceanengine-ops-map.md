# 第 34 章　巨量实操地图：从“知道概念”到“知道后台每一步在干什么”

> 核验日期：2026-09-17。后台菜单、字段名称与白名单政策可能继续变化。本章把“当前官方链路”和“长期有效的操作逻辑”分开写。

这一章的目标不是教你背菜单，而是让你第一次打开巨量和抖音小游戏后台时，知道每一个页面到底解决什么问题、哪个页面出错会导致什么后果，以及你应该按什么顺序完成投前准备。

## 1. 先画出两套后台的边界

对抖音小游戏信息流投放，新手最容易犯的错，是把“小游戏开发者平台”和“巨量引擎广告投放平台”当成一个系统。实际上你需要同时理解两套后台：

**抖音小游戏开发者平台**负责小游戏本身：主体、小游戏 AppID、版本、正式线上版本、推广能力、增长分析、收入和投放相关能力。

**巨量引擎广告投放平台**负责广告：广告账户、推广对象、转化目标、广告组/计划/素材、预算、出价、数据看板和财务。

这里必须先做一个分流判断：你跑的是**小游戏直投**，还是**微端投放**。直投的用户点击广告后直接进入抖音小游戏；微端则额外引入移动应用资产、巨量 AppID 和 .miniapk。所以“微端包包名、移动应用资产”不是所有小游戏投放都必须有，而是微端链路专属。

如果这几项之间绑定错了，你会遇到非常典型的故障：计划能建但没有转化、事件有数据但归不到广告、包审核通过却选不到应用、小游戏有收入但媒体侧找不到对应计划。

## 2. 当前官方链路：先分直投和微端

截至本章核验日期，官方首页明确存在“直投买量”，定义为信息流广告点击后直接跳转抖音小游戏；官方结算/对账文档同时把投广场景列为“微端和直投”。因此下面原先写成“主链路”的内容，实际上只是**微端专项链路**：

1. 创建并上线抖音小游戏；
2. 在小游戏后台获取小游戏 AppID；
3. 根据小游戏 AppID 确认微端包包名；
4. 在巨量后台创建移动应用资产并申请巨量 AppID；
5. 回到小游戏平台，把巨量 AppID 与对应小游戏绑定，获取正式微端包；
6. 在巨量移动应用资产中上传正式微端包，完成审核；
7. 在事件管理中完成投放所需事件配置/检测；
8. 创建广告并开始投放；
9. 在巨量侧查看实时投放数据，在小游戏侧查看更长周期的回收数据。

当前官方 miniapk 文档还明确写到：**微端投放**目前仅支持安卓平台；该专项指南列出的流量范围主要支持抖音与头条客户端，并支持激活、关键行为、付费相关目标和付费 ROI。注意这些“安卓/应用包”限制是在讲微端，不能反推成“抖音小游戏本体只能按 APK 投”。实际可见目标和直投入口仍应以你的账户权限与当前后台为准。

官方参考：
- 直投买量场景：https://developer.open-douyin.com/
- 对账口径（投广来源含微端和直投）：https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/guide/business-guide/revenue/introduction/mini-game-reconciliation-guide
- 微端专项：https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/guide/business-guide/advertiser/miniapk/guidelines

## 3. 操作前不要急着点“新建广告”

一个职业投手不会拿到账号就点创建计划，而会先做“资产检查”。建议固定成一张投前表：

| 检查项 | 要回答的问题 | 不通过的后果 |
|---|---|---|
| 主体 | 小游戏主体与广告账户主体是什么关系 | 授权、投放金、资质可能出问题 |
| 小游戏状态 | 是否已上线、版本是否正确 | 微端和推广能力不可用 |
| AppID | 小游戏 AppID 是否记录正确 | 包名、绑定、归因链路出错 |
| 巨量应用资产 | 是否创建了正确的安卓应用 | 建计划时选错应用 |
| 巨量 AppID | 是否与小游戏正确绑定 | 微端包链路断裂 |
| 微端包 | 是否是正式包而非测试包 | 审核/投放失败 |
| 应用审核 | 当前包是否审核通过 | 无法正常投放 |
| 事件 | 激活及后续事件是否可用 | 模型没有反馈信号 |
| 财务 | 余额、赠款/投放金、账户状态是否正常 | 计划无法消耗 |
| 素材 | 是否有明确编号与假设 | 后续无法复盘 |

第一次投放时，这张表比任何“调价技巧”都重要。

## 4. AppID、包名、应用资产：先确认你是否在走微端

如果是**直投**，不要看到教程里的“包名/移动应用资产”就机械照做；这组对象主要服务于微端应用链路。下面关于微端包名、巨量 AppID 与移动应用资产的内容，默认属于微端分支。

### 4.1 小游戏 AppID

这是小游戏在抖音开放平台中的身份。它决定了你在开发者平台里操作的是哪一个小游戏，也用于生成微端相关包名。

### 4.2 微端包名

官方当前文档给出的基础格式是：

`com.bytedance.<小游戏AppID>.miniapk`

不要手抄后直接相信。真正操作时必须从后台和官方规则核对，因为分包、历史包或后续规则更新可能带来差异。

### 4.3 巨量 AppID / 移动应用资产

这是广告投放侧使用的应用资产标识。职业上要建立一个习惯：**所有应用资产都做映射表**。

示例：

| 内部游戏名 | 小游戏 AppID | 巨量 AppID | 包名 | 巨量账户 | 当前版本 |
|---|---|---|---|---|---|
| 飞机A | tt_xxx | 123456 | com.bytedance... | Account-A | 1.3.2 |

如果以后同时跑多个包、多个账户，这张表会救你很多次。

## 5. 事件管理到底是干什么的

很多新手理解事件管理为“报表埋点页面”，这是不够的。对于投放系统来说，事件管理是告诉模型：

> 我花钱以后，什么样的用户算成功？

激活只是最浅的成功定义。关键行为、付费、ROI 是更深的成功定义。

因此事件管理问题会直接变成算法问题：

- 激活回传漏 20%，模型看到的训练样本就残缺；
- 关键行为定义过深，样本太稀疏，计划可能难以学习；
- 关键行为定义与长期价值无关，模型会非常努力地找到“会做这个动作但不值钱”的人；
- 付费金额口径错，ROI 优化方向会被直接带偏。

所以你进入事件管理页面时，不是在“做技术配置”，而是在给投放系统定义奖励函数。

## 6. 当前官方对事件和归因的几个重要说明

截至本章核验日期，官方指南说明小游戏微端场景下，字节内部已经打通基础投放归因链路；同时支持在事件管理中配置第三方监测链接，并通过 OPENID 宏参进行更细粒度归因。巨量侧可查看较短周期实时投放数据，小游戏开发者平台可用于更长周期的离线回收评估。

这些能力对新手最重要的意义不是“可以少写代码”，而是：**你必须事先决定公司到底以哪个系统作为哪类指标的最终口径。**

推荐至少定义：

- 消耗、展示、点击：媒体后台为主；
- 激活/关键行为：媒体归因口径 + 自有埋点对账；
- 留存：自有用户口径为主；
- 广告收入：平台结算/自有广告收入数据明确口径；
- 内购收入：订单系统或平台结算口径；
- LTV：统一 Cohort 口径计算。

## 7. 建广告之前，你要先写“实验卡”

不要先建计划再想这条计划要测什么。正确顺序是先写：

**实验问题**：怀旧街机包装是否比二次元包装带来更高 D1 与广告 ARPU？

**主变量**：素材包装风格。

**保持不变**：转化目标、预算、时段、应用、核心定向、落地链路。

**主指标**：合格激活成本、D1、首日广告 ARPU。

**辅助指标**：CTR、CVR、激活成本。

**停止条件**：达到预设样本后后端质量显著低于对照；或链路异常。

没有实验卡，你后面看到所有数据都容易“事后解释”。

## 8. 第一条计划的目标不是赚钱

第一条计划更现实的任务是验证：

1. 广告能否正常审核；
2. 能否正常消耗；
3. 点击到游戏链路是否通；
4. 激活是否被正确记录；
5. 自有数据与媒体数据能否对账；
6. 收入事件是否能进入正确 Cohort；
7. 素材编号和计划编号能否被追踪。

在这些都没验证前，就讨论“这款游戏的 CPI 为什么高”，通常太早。

## 9. 一个实操故障树

### 情况 A：广告完全不消耗

先按顺序查：

账户状态 → 余额 → 审核状态 → 应用资产 → 广告位/流量设置 → 出价/预算 → 定向是否过窄 → 计划是否处于可投状态。

不要第一反应就加价。

### 情况 B：有点击，没有激活

查：

点击链路 → 微端包 → 加载失败 → 事件配置 → 归因 → 数据延迟。

先用真实设备走一次完整路径。

### 情况 C：媒体有激活，自有后台没有

查用户定义、时间窗、去重规则、OPENID/用户标识映射和服务端事件。

### 情况 D：媒体 CPA 正常，但游戏完全不赚钱

这通常不是“后台配置问题”，要回到：素材承诺、用户质量、首局体验、关键行为相关性、广告/付费变现。

## 10. 本章作业

不要只读。请为你自己的游戏制作一张《投前资产地图》，至少包括：主体、小游戏 AppID、巨量 AppID、包名、版本号、广告账户 ID、应用资产、事件列表、收入数据源、留存数据源、素材编号规则。

然后画一张箭头图：

`素材 → 广告计划 → 点击 → 微端启动 → 激活 → 首局 → 关键行为 → 广告/付费 → D1 → D7 → LTV`

对每一个箭头回答两个问题：

1. 谁记录这个数据？
2. 断了以后去哪里查？

能完成这张图，才算真正具备第一次实操的基础。
