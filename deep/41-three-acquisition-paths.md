# 第 41 章　三种抖音系买量链路：小游戏直投、小游戏微端、原生 Android APK

> 核验日期：2026-09-23。平台菜单和账户权限会变化。本章只把三条链路的产品关系、资产关系、数据关系和投放步骤讲清楚。具体按钮以投放当天后台为准。

这一章解决一个很实际的问题：

**同一个游戏，既可以有抖音小游戏版本，也可以有 Android 原生 APK。那在抖音/巨量体系里，到底有几种投法？它们有什么区别？**

先给结论：

1. **小游戏直投**：广告点击后直接进入抖音小游戏。
2. **小游戏微端**：平台把小游戏包装成可安装的 Android 微端，再走应用推广链路。
3. **原生 Android APK**：推广你自己真正开发、独立安装运行的 Android App。

第 2 和第 3 看起来都“有 APK/包”，但本质完全不同。

---

## 41.1 三条链路先画在一张图里

### 路线 A：小游戏直投

```
信息流广告
  ↓
点击
  ↓
直接打开抖音小游戏
  ↓
进入首局
  ↓
广告 / 内购
  ↓
留存 / LTV / ROAS
```

核心特点：

**用户不需要下载安装你的原生 App。**

官方当前把“直投买量”描述为信息流广告点击后直接跳转到抖音小游戏；官方小游戏对账文档也明确把投广来源分为“微端和直投”。

### 路线 B：小游戏微端

```
信息流广告
  ↓
Android 微端安装 / 启动
  ↓
微端承载小游戏
  ↓
小游戏实际内容
  ↓
广告 / 内购
  ↓
留存 / LTV / ROAS
```

微端不是重新做了一套 Android 游戏。

它更接近：

> **把抖音小游戏包装成一个可安装的 Android 应用载体。**

官方早期对微端的解释就是“包装成 APP 的小游戏”；当前正式文档仍然要求小游戏 AppID、巨量 AppID、微端包、移动应用资产等链路。

### 路线 C：原生 Android APK

```
信息流广告
  ↓
应用下载
  ↓
安装你自己的 Android APK
  ↓
启动原生游戏客户端
  ↓
注册 / 创角 / 首局
  ↓
广告 / 内购
  ↓
留存 / LTV / ROAS
```

这里运行的是**你自己真正开发的 Android 客户端**。

它不是抖音小游戏，也不是 miniapk。

它属于标准的**应用推广 / 内容下载**业务。

---

## 41.2 一张表看懂三者差别

| 维度 | 小游戏直投 | 小游戏微端 | 原生 Android APK |
|---|---|---|---|
| 真正产品 | 抖音小游戏 | 抖音小游戏 | Android 原生 App |
| 是否独立安装 | 否 | 是，安装微端 | 是，安装原生 App |
| 包是谁生成 | 不需要 Android 包 | 平台为小游戏生成微端包 | 研发自己构建 APK |
| 游戏代码主体 | 小游戏代码 | 仍是小游戏代码 | 原生 Android 客户端 |
| 小游戏 AppID | 核心资产 | 核心资产 | 通常不是核心资产 |
| 巨量移动应用资产 | 视当前直投链路而定 | 必须涉及 | 应用推广必然涉及 |
| Android 包名 | 无原生 APK 包名 | com.bytedance...miniapk 等微端包名 | 你自己的 package name |
| 用户点击广告后 | 直接进小游戏 | 下载/安装微端后进入小游戏 | 下载/安装原生 App |
| 数据核心 | 小游戏增长 + 巨量投放 | 微端归因 + 小游戏收入/行为 | App 激活/事件 + 自有 BI |
| 适合解决的问题 | 最短链路买小游戏用户 | 扩展应用下载型分发 | 获取独立 App 用户 |
| 是否等于“小游戏上架” | 是小游戏买量 | 是小游戏买量的一种载体 | 不是小游戏买量 |

这里最重要的一句话是：

> **“有一个 APK”并不代表它是微端；“有一个微端包”也不代表你拥有一个独立原生 Android 游戏。**

# 第一部分：小游戏直投

## 41.3 直投为什么应该先学

如果你的商业目标就是：

> 给已经上线的抖音小游戏买用户。

那么从理解难度上，直投是最容易建立正确心智模型的一条链路：

**广告 → 小游戏。**

没有额外的安装包概念。

这意味着你分析漏斗时，主要关注：

```
展示
→ 点击
→ 进入小游戏
→ 有效激活 / 有效进入
→ 首局
→ 关键行为
→ 广告 / 付费
→ 留存
→ LTV
```

而不是先分析“下载率、安装率”。

官方小游戏对账文档当前明确把“直投”列为投广场景之一，因此直投产生的用户与自然量、发行人计划等流量在经营分析上也要分开。

---

## 41.4 直投的资产检查

做直投前至少整理：

| 资产 | 要确认什么 |
|---|---|
| 小游戏主体 | 谁是开发者主体 |
| 小游戏名称 | 正式线上名称 |
| 小游戏 AppID | 是否正确 |
| 正式版本 | 当前投放的版本 |
| 巨量广告账户 | 哪个账户花钱 |
| 主体关系 | 是否存在授权关系 |
| 转化目标 | 激活 / 关键行为 / 付费 / ROI 等当前可用能力 |
| 自有 BI | 能否识别投放新增 |
| 收入 | IAA / IAP 数据从哪里取 |
| 素材 ID | 能否追溯到素材假设 |

特别注意：

直投链路里**不要为了照教程而去找 miniapk 包名**。

如果你当前广告产品走的是直投，就按直投资产核对。

# 第二部分：小游戏微端

## 41.5 微端到底解决什么问题

微端的价值不是“把小游戏变成原生游戏”。

它解决的是：

**让小游戏能够以一个轻量 Android 应用的形式进入应用推广/下载型流量链路。**

这意味着你可以利用传统 App 下载型广告的一些分发和优化逻辑，同时实际承载的仍然是小游戏。

官方微端指南当前明确：

- 微端只支持 Android 投放；
- 需要小游戏 AppID；
- 需要申请/建立巨量 AppID；
- 需要在小游戏平台绑定；
- 需要获取正式微端包；
- 需要在巨量移动应用资产中上传并审核；
- 当前指南支持激活、关键行为、付费及付费 ROI 等目标；
- 当前指南说明流量支持抖音、今日头条两个客户端。

这些是**微端专项规则**，不要套到直投或原生 APK 上。

---

## 41.6 微端完整资产链

微端可以按下面这张图理解：

```
抖音小游戏
  │
  ├── 小游戏 AppID
  │
  ↓
巨量侧申请应用 / AppID
  │
  ↓
回小游戏开发者平台绑定巨量 AppID
  │
  ↓
生成正式 miniapk
  │
  ↓
巨量移动应用资产上传 / 审核
  │
  ↓
事件管理 / 数据检测
  │
  ↓
建立应用类投放
  │
  ↓
广告 → 安装微端 → 进入小游戏
```

这也是为什么微端教程看起来比直投复杂很多。

它多出了一层：

**“Android 应用资产包装层”。**

---

## 41.7 微端从零操作顺序

### Step 1：小游戏先正常上线

不要倒过来。

先保证小游戏正式版本本身正常：

- 主体完成认证；
- 游戏版本通过审核；
- 正式环境可进入；
- AppID 记录正确；
- 隐私协议、资质等一致。

### Step 2：记录小游戏 AppID

官方当前的微端包名规则以小游戏 AppID 为基础。

官方示例格式：

```
com.bytedance.<小游戏AppID>.miniapk
```

实际操作时以开发者后台生成的信息为准，不要自己手写包名后直接拿去用。

### Step 3：在巨量侧建立对应应用资产

进入巨量广告平台的移动应用资产体系，为这条微端链路建立对应的应用，并获取巨量侧 AppID。

注意：

这个 AppID 和抖音小游戏 AppID 是两个东西。

必须建立映射：

| 字段 | 示例 |
|---|---|
| 内部项目 | Game-A |
| 小游戏 AppID | tt_xxx |
| 巨量 AppID | 123xxx |
| 微端包名 | com.bytedance.tt_xxx.miniapk |
| 广告账户 | Account-A |

### Step 4：小游戏平台绑定巨量 AppID

回到小游戏开发者平台的投放相关能力中，把正确的巨量 AppID 绑定到小游戏。

官方当前文档提示，微端能力可能涉及权限/白名单申请。

所以如果入口不存在，不要直接认为“教程过时”。

先查：

- 小游戏状态；
- 账号权限；
- 主体；
- 是否已开通微端能力；
- 是否需要联系销售/直客申请。

### Step 5：生成正式微端包

拿到正式微端包后检查：

- 包名；
- 对应小游戏；
- 对应巨量 AppID；
- 生成时间；
- 版本；
- 主体。

不要把测试包和正式包混用。

### Step 6：上传巨量应用资产并审核

把正式微端包放进巨量侧应用管理。

这一步本质是在告诉广告系统：

> “这个 Android 应用资产，对应的是这个小游戏的微端。”

审核失败时应该记录拒绝原因，不要只反复提交。

### Step 7：事件与归因

官方当前微端文档说明，字节内部已打通基础数据链路；同时还支持通过 OPENID 宏参数和第三方监测做更细归因。

投前至少检查：

- 激活有没有数据；
- 关键行为是否正确；
- 付费金额口径是否正确；
- 游戏 BI 是否能找到对应新增；
- 媒体侧与自有数据差异是否在可解释范围。

### Step 8：创建广告

然后才进入：

- 推广对象；
- 转化目标；
- 流量位置；
- 定向；
- 素材；
- 出价；
- 预算。

顺序不要反过来。

---

## 41.8 微端的漏斗与直投不一样

直投更像：

```
点击 → 进入小游戏
```

微端多了一层：

```
点击 → 下载 / 安装 → 启动微端 → 进入小游戏
```

所以出现成本异常时，故障树也不同。

例如：

**CTR 正常，但是激活成本突然变高。**

直投优先查：

- 点击到小游戏进入率；
- 小游戏启动；
- 加载；
- 事件。

微端则还要加：

- 下载；
- 安装；
- 包审核/版本；
- Android 兼容；
- 微端启动。

这就是为什么不能把两种链路的 CVR 混着看。

# 第三部分：原生 Android APK

## 41.9 原生 APK 是另一套产品，不是微端升级版

如果你的团队本来就有一个独立 Android 游戏：

```
com.company.game
```

玩家下载安装后，即使完全没有抖音 App，也能独立启动和运行。

那么它属于**原生 Android App**。

这和微端最大的区别是：

**微端的核心产品还是小游戏；原生 APK 的核心产品就是 App 自己。**

因此在巨量体系里，它应该进入标准的**应用推广 / 内容下载**逻辑。

巨量引擎当前官网仍把“内容下载”作为独立营销场景，并针对应用下载行业提供激活、付费、ROI、次留等深度目标解决方案。

---

## 41.10 原生 APK 的完整链路

最简化可以理解成：

```
原生 Android 游戏
  ↓
正式签名 APK / 应用资产
  ↓
巨量广告账户
  ↓
Android 应用推广对象
  ↓
转化追踪
  ↓
广告素材
  ↓
下载 / 安装
  ↓
激活
  ↓
注册 / 创角 / 首局
  ↓
付费 / 广告收入
  ↓
D1 / D7 / LTV
```

这里已经没有“抖音小游戏 AppID → miniapk”这层关系。

---

## 41.11 APK 投放前准备什么

至少准备：

### 产品资产

- Android 正式版本；
- package name；
- versionCode / versionName；
- 正式签名；
- 隐私政策；
- 软件著作权、版号及平台要求的游戏资质；
- 下载地址或平台要求的应用资产。

### 广告资产

- 巨量广告账户；
- Android 应用推广对象；
- 应用审核状态；
- 素材；
- 落地/下载链路；
- 转化追踪。

### 数据资产

- 设备/用户 ID 体系；
- 激活；
- 注册；
- 创角；
- 首局完成；
- 关键关卡；
- 广告观看；
- 首次付费；
- 付费金额；
- 留存；
- LTV。

对于原生 APK，**你自己的数据体系重要性更高**。

因为最终用户价值存在你的 App 和服务器里，而不是小游戏平台帮你天然统一管理。

---

## 41.12 APK 应用推广在巨量里买的是什么

巨量官网当前把“内容下载”作为独立营销业务，并且应用下载/游戏解决方案中明确存在：

- 激活；
- 激活且付费；
- 次留类优化；
- 付费相关优化；
- ROI 类优化；
- IAA 场景下的深度变现优化。

具体某个账户能看到哪些目标，以当前后台权限为准。

新手不要犯一个错误：

> 原生 APK 一上来就选最深的 ROI 目标。

还是要回到本书前面的“信号密度”原则。

如果一天只有极少付费用户，模型很可能没有足够的训练反馈。

可以按：

```
激活
→ 高相关关键行为
→ 付费
→ ROI / LTV 代理
```

逐步深化。

---

## 41.13 APK 最关键的是转化追踪

原生 App 买量和小游戏买量最大的工作差异之一，就是：

**App 内发生的事情必须可靠地回到投放系统和自有 BI。**

例如：

用户点击广告 → 下载 → 安装 → 第一次打开。

平台需要知道：

> 哪一次广告带来了这个激活。

再往后：

用户付费 6 元。

系统还需要知道：

> 这 6 元属于哪一批投放用户。

否则就只能优化点击和下载，不能真正优化用户价值。

实际接入可以使用平台当前支持的应用转化追踪方案、SDK/API 或第三方监测体系；具体方式以当前账户和官方技术文档为准。

无论用哪种技术，验收标准都是一样的：

```
媒体广告 ID
→ 安装
→ 激活
→ 用户
→ 行为
→ 收入
→ Cohort
```

必须能逻辑闭环。

---

## 41.14 APK 的第一轮测试怎么看

原生 APK 比小游戏多出一个非常关键的转化层：

**下载 / 安装。**

因此漏斗建议至少拆成：

| 层级 | 指标 |
|---|---|
| 曝光 | CPM |
| 点击 | CTR / CPC |
| 下载 | 点击→下载 |
| 安装 | 下载→安装 |
| 激活 | 安装→首次启动 |
| 首局 | 激活→首局完成 |
| 留存 | D1 / D3 / D7 |
| 变现 | IAA ARPU / 付费率 / ARPPU |
| 长期 | D7 / D30 LTV、ROAS |

所以一个 APK 广告：

**CTR 很高但激活成本很差**

可能不是素材问题，而是：

- 下载页面；
- 包体太大；
- 下载失败；
- Android 兼容；
- 安装拦截；
- 安装后启动失败。

这些问题在小游戏直投里根本不存在。

# 第四部分：三条链路怎么同时管理

## 41.15 不要把三条链路的用户混成一个 Cohort

假设同一天：

- 直投花 3000；
- 微端花 3000；
- 原生 APK 花 3000。

最后一共新增 1500 人。

你绝对不能只算：

```
总成本 9000 / 总新增 1500 = 6 元
```

然后说“我们的获客成本是 6 元”。

因为三条链路的：

- 进入门槛；
- 用户意图；
- 平台环境；
- 支付环境；
- 广告变现环境；
- 留存；
- 数据口径；

都可能不同。

至少分成：

```
channel = douyin_direct
channel = douyin_miniapk
channel = android_native
```

再进一步拆：

```
campaign
creative
cohort_date
```

## 41.16 推荐的资产台账

| 项目 | 直投 | 微端 | 原生 APK |
|---|---|---|---|
| 项目 ID | MG-DIRECT | MG-MINIAPK | ANDROID-NATIVE |
| 产品版本 | 小游戏 1.2 | 小游戏 1.2 | Android 2.3 |
| 小游戏 AppID | 有 | 有 | 无/非核心 |
| 巨量 AppID | 按当前直投能力 | 有 | Android 应用资产 |
| 包名 | 无原生安装包 | miniapk 包名 | 自有 package name |
| 广告账户 | A | A/B | B |
| 转化目标 | 激活/关键行为 | 激活/关键行为 | 激活/付费/ROI |
| 收入来源 | 小游戏平台/BI | 小游戏平台/BI | 自有服务器/广告平台 |
| Cohort 标签 | direct | miniapk | native |

这个表长期维护。

---

## 41.17 三条链路什么时候各自有意义

这不是“哪个更高级”的关系。

### 直投

当你的核心目标就是快速给抖音小游戏买量，减少额外安装步骤时，优先把它理解清楚。

### 微端

当你希望利用应用下载型流量/能力扩展小游戏分发，且账户具备微端能力时，可以作为第二条独立测试链路。

### 原生 APK

当你本身有一个值得长期经营的 Android 原生版本，希望建立独立 App 用户资产、独立版本和更完整客户端能力时，它应该作为独立发行产品来做。

原生 APK 的成败不能用“小游戏买量好不好”简单解释。

---

## 41.18 一个很重要的实验：同素材，三链路不要直接比 CPI

假设同一条“Boss 战”素材：

| 链路 | 前端成本 |
|---|---:|
| 直投 | 4.5 |
| 微端 | 5.8 |
| APK | 7.2 |

不能直接说：

> 直投最好。

因为 7 天后可能是：

| 链路 | D7 LTV |
|---|---:|
| 直投 | 4.9 |
| 微端 | 7.2 |
| APK | 10.5 |

那么真正应该比较的是：

```
获客成本
+
回收曲线
+
规模
+
现金流
+
用户资产价值
```

而不是只比较 CPI。

---

## 41.19 给新手的正确学习顺序

如果你三条链路都要做，建议按这个顺序学：

### 第一阶段：小游戏直投

先学：

- 广告；
- 激活；
- 素材；
- Cohort；
- IAA/IAP；
- ROI。

因为链路最短，最容易理解“素材到底带来了什么用户”。

### 第二阶段：小游戏微端

再增加：

- Android 应用资产；
- 巨量 AppID；
- miniapk；
- 下载/安装；
- 微端归因。

### 第三阶段：原生 APK

最后再建立真正独立的：

- App 版本体系；
- 应用资产；
- 安装归因；
- 服务端用户；
- 支付；
- 广告收入；
- LTV；
- 多渠道归因。

这样概念不会打架。

---

## 41.20 本章作业

给你自己的项目画三张图。

第一张：

```
广告 → 小游戏直投 → 首局 → 收入
```

第二张：

```
广告 → 微端下载 → 微端启动 → 小游戏 → 收入
```

第三张：

```
广告 → APK 下载 → 原生 App 激活 → 首局 → 收入
```

然后对每个箭头写清楚：

1. 谁记录？
2. 哪个后台能看？
3. 谁是最终口径？
4. 如果断了，第一步查哪里？

如果三张图画完以后还有两个指标共用同一个名字但含义不同，例如两个“激活”，就马上重命名。

因为真正进入多版本、多渠道发行后，**口径混乱比投放贵更危险。**
